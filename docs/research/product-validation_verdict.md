# Prompire: standalone product assessment

**Verdict: `YES, BUT`.** Prompire has a real, unduplicated core — a definition of done pinned outside the agent's reach before work begins, with the verdict computed from the repository's actual state afterward, needing no agent cooperation — and it sits in a category (post-hoc agent-work verification) that verifiably exists but has no consolidated incumbent: nothing comparable on GitHub exceeds ~100 stars, and platform vendors are commoditizing *prevention* (sandboxes, deny rules), not verification. But a launch today would hit one genuine code defect on the modal task (a brief that legitimately allows test edits can never get its acceptance commands run by `prompire verify`), one falsifiable overclaim in the threat model (gitignored paths are invisible to the diff authority, while the docs claim "git sees the write whatever tool made it"), and a README that markets a failure its own benchmark never observed while burying the failure its benchmark reproducibly demonstrates. These are days of work, not months — which is exactly why the verdict is "YES, BUT" and not "NOT YET." An earlier draft of this assessment said "NOT YET" on four blockers; a fresh-context adversarial review killed two of them against the code (details in §11), and a verdict calibrated to the surviving two does not justify withholding the launch that is also the only available instrument for validating demand.

## 1. Strongest reason Prompire should exist

No substitute — instructions, sandboxes, deny rules, CI, branch protection, PR review, worktrees, or any combination — provides this property: the scope, the executable acceptance commands, their measured baseline, and the base commit are all fixed *before* the agent starts, in a form the agent cannot silently edit, and the verdict is read from the real git diff afterward. VERIFIED live by two independent agents: widening the scope of an armed brief produces no verdict at all (exit 2) rather than a favorable one, and the naive "10-line shell script" replication fails on the first realistic input, because `git diff --name-only` misses untracked additions — the exact class the shipped demo catches — and judges only the destination side of renames.

## 2. Strongest reason Prompire may fail

The purchase trigger is structurally invisible. The failure Prompire insures against — a run that *looks* clean because the agent edited the grading surface — is by definition the failure users don't see, so it generates no install intent; and the value users *can* see (scope discipline, explicit acceptance criteria) looks copyable into a prompt template. A failure you never observe generates no demand, and Prompire's own instrument can't cite an in-the-wild base rate. HYPOTHESIS supported directionally, not numerically: METR measured o3 reward-hacking 43× more often when the scoring function was visible and modifiable; Cursor found 63% of Opus SWE-bench Pro "resolutions" retrieved rather than derived the fix. The event concentrates in exactly the hard, stuck runs users most want to trust — but nobody has field data, including Prompire.

## 3. Ideal initial user

A developer running several **unattended** agent sessions per day — serial heavy delegation or a small parallel fleet — in a repo where the test suite is the de-facto grading function, with no second human reviewer in the loop (solo or 2-3 person team, so CODEOWNERS on tests is inert). The version of this user for whom the friction argument dissolves entirely: one whose briefs are drafted by an orchestrating model (`draft --agent` exists for this) and merely confirmed by the human. Notably, that is how this repo itself is developed.

## 4. Product wedge

```text
USER:      solo dev / 2-3 person team delegating multiple unattended tasks daily
WORKFLOW:  tasks big enough that nobody reads the transcript or every diff line;
           brief drafting delegated to a model, human confirms the marked lines
RISK:      a run that looks clean — green suite, plausible summary — because the
           grading surface (tests, harness, comparison base) moved, or because
           work drifted outside what was asked
TRIGGER:   burned once post-merge, or scaling to parallel runs where per-run
           human attention is mathematically unavailable
ADVANTAGE: the only layer that checks finished work against a contract fixed
           before the work began, from evidence the agent cannot silently edit
```

## 5. Category and positioning

**Call itself:** a *verification tool for delegated agent work* — an independent examiner. The auditor framing makes "doesn't my sandbox do this?" answer itself: an auditor composes with door locks.

**One-sentence positioning:** "Your agent's success signal is generated by the agent; Prompire recomputes it from the repository, against a contract pinned before the work started."

**Avoid calling itself:** guardrail, scope *guard*, sandbox-adjacent anything, prevention, safety tool. Every prevention word invites comparison with the layer platforms are commoditizing and that Prompire's own threat model calls a "speed bump." Also avoid leading with "agents cheat on tests": the README's headline claim ("will, sooner or later, edit the suite") is the one claim its own 90-run benchmark cannot support — zero tamper events observed — while the reproducible campaigns *do* support "undirected agents drift out of scope and miss contracts" (all nine scope violations in the `bare` arm; `plus_acceptance` 5/5). Lead with drift and done-ness; keep tamper-evidence as the trust anchor and cheating as the tail risk it also covers. One honest caveat forced by adversarial review: the zero-tamper result cannot *disprove* the cheating premise either — every benchmark run used a prompt announcing the external check, on easy, short tasks; the benchmark was never powered to observe reward hacking. The evidence licenses "drift-first," not "cheating is a myth."

## 6. Substitute analysis

| Substitute | What it already solves | Remaining Prompire advantage | Strength |
|---|---|---|---|
| Doing nothing + skimming `git diff` | Catches blatant drift, free | Contract exists before the diff does; baseline separates pre-existing red from breakage; pinned base defeats agent-committed empty diffs; untracked files seen | **Strong**, scaling with task volume and diff size |
| CLAUDE.md / AGENTS.md instructions | Cheap behavioral nudge; mostly followed | Instruction is input to the actor; Prompire checks the output. Only the check tells you the instruction worked | **Strong** (different layer, not competing) |
| Claude Code deny rules / hooks | Blocks watched-tool writes pre-hoc | Replicates only Prompire's weakest layer (its own hook); no per-task contract, no baseline, no verdict. Bash bypasses both | **Strong** on the checker, nil on the hook |
| Containers / sandboxes | Real kernel-level blast-radius control | The sandbox boundary is the workspace, not the task; test-gaming happens entirely inside it | **Strong** (cleanest complement) |
| CI | Runs unconditionally; honest merge-base | Grades with the suite the agent may have edited; a hand-rolled "tests unchanged" check covers the headline case in ~20 lines but has no baseline/transition/tests_policy semantics. Prompire's own ci.md concedes the PR-author-controls-the-brief hole | **Marginal-to-moderate** (weakest deployment mode, honestly documented) |
| PR review + branch protection + CODEOWNERS on tests | For teams, a second human on any test change covers the headline failure with stock GitHub | Scope allowlist and baseline remain; but for solo devs CODEOWNERS is inert and Prompire is the only structured reviewer | **Marginal for teams, strong for solo** |
| Worktrees | Isolation, clean per-task diffs | Isolation ≠ verification; worktrees are an input to Prompire's happy path (its own threat model prescribes one brief per worktree) | **Strong** (complement) |
| Existing OSS (agent-guardrails ×3, agent-contracts, codex-protect, TAKT...) | Fragments of the idea | All pre-traction (≤~100 stars); the closest one is MCP-based, i.e., the *agent calls the verification tools* — the trust model Prompire exists to reject | **Strong** (no incumbent; also no proven demand) |

## 7. Workflow-tax analysis

Measured by actually walking the loop (VERIFIED): install is near zero; `prompire demo` (2.7s) is the best UX moment in the product; steady-state cost is ~5 commands and 2-4 minutes per task — defensible for hour-long delegations. First use cost ~20-40 minutes, dominated by refusal-loop debugging.

**Essential friction** (required by the guarantee): thinking through scope, the acceptance command, and tests_policy; the `# prompire:unconfirmed` confirm-each-line gate; the refusal to verify an edited armed brief; recording every disarm durably. **Also essential, though an earlier draft misclassified it:** the `close`→`repin`→`--ack-disarms` cycle. Adversarial review established this is deliberate anti-laundering design with a shipped remedy (the digest is printed at close *and* inside the failing REVIEW), not a bug — but it is real repeat-use friction (a fresh digest copy per task, never scriptable) and deserves UX polish: a close that records "clean verdict existed at close time" could spare honest users the treadmill without reopening the laundering hole.

**Accidental friction** (fixable without weakening anything): the verify dead-end for `named`/`authoring` briefs (§11, the one true code blocker); a failed-lint `prepare` persisting the baseline block into the brief, forcing hand-editing; Prompire's own baseline run dirtying the tree with `__pycache__` and then refusing the retry; the raw-JSON leakage in verify's human output; no documented between-tasks reset or mid-task brief-revision procedure (the naive path suggests `dirty_baseline`, which would quietly gut the verdict — the safe stash dance is documented nowhere).

## 8. Minimum lovable workflow

The guarantee needs exactly three events: **pin** before work (base commit + contract digest outside the agent-editable file), **verdict** after work (real diff against the pin plus re-run of pre-measured acceptance), and a durable **record** of any disarm. The current verb skeleton (`prepare` / `verify` / `close`) maps to these almost exactly — honest finding: it is already close to minimal; the defects are at the edges, not in the shape. The minimum human input is: one goal sentence, confirmation of the acceptance command, and confirmation of a derived scope. Everything else can default (`forbidden: []`, `autonomy: ask`, `tests_policy: immutable` unless scope touches test paths) or is already automated (baseline, base_rev, transitions). `close` as a separate ceremony could fold into `verify --done` or auto-trigger on the next `prepare`, keeping the tombstone. An optional `prompire run -- <agent-cmd>` wrapper (launch agent, auto-verify on exit) would remove two of the five steady-state steps without weakening anything, since verify is read-only.

## 9. Viral demonstration

**Keep the shipped drift demo as the canonical one** — agent completes the task correctly *and also* writes `secrets.cfg`, an untracked file outside scope; caught from the pinned diff; "nothing it could claim would hide the extra file." An earlier draft of this assessment chose the staged test-edit demo instead; adversarial review correctly flagged that as inconsistent with the drift-first positioning and no more honest than the current demo (both are scripted). The drift demo also happens to showcase exactly what the naive shell replication misses (untracked additions). The test-edit-under-`immutable` catch belongs as the *second* beat of the same demo, and the demo should gain a third beat it currently lacks: scope clean but acceptance red — the done-ness story. Three beats, one throwaway repo, no threat-model lecture.

## 10. Ten hostile launch questions

1. **"Why isn't this `git diff --exit-code` plus YAML I read myself?"** Strongest answer: the diff is the easy half; the pin, whole-file digest, untracked/rename/skip-marker handling, and the lint that refuses uncheckable briefs are the 924 lines the shell script converges toward after it's wrong the first time. Docs: well covered (README, rules.md B16). Satisfactory — win it by demonstration (see gate 6).
2. **"What stops the agent from modifying Prompire itself?"** Watched tools can't touch `ACTIVE`/tombstones at any spelling (verified, 11-probe test); Bash can forge a clean `pin` in three commands (live-reproduced) and the docs say so — evasion becomes overt, not impossible. Unresolved half: a repo-vendored `check_scope.py` is agent-editable and then reports on its own tampering; no doc says "run the verifying copy from outside the workspace." Needs one sentence in hosts.md.
3. **"The hook doesn't watch Bash — isn't the guard theater?"** The hook is a declared speed bump; the authority is the post-hoc diff, which sees Bash writes. Docs unusually thorough, including the sharp caveat about Bash-prompts-while-Edit-auto-accepts configurations. Satisfactory — after fixing the `check_scope.py --activate` diagnostic message that unconditionally claims "writes outside scope are refused before they happen" whether or not any hook is installed (VERIFIED at check_scope.py:269; note `prepare` discards this line — it's a diagnostic-path fix, not a primary-flow lie).
4. **"The agent can trojan `node_modules`/`.venv` and your acceptance runs it."** Currently **no good answer** — gitignored paths never enter the diff authority (live-reproduced: clean verdict over a planted ignored file), and the threat model's "git sees the write whatever tool made it" is falsifiably wrong for ignored paths. The credibility of a "every known limitation, in full" document requires fixing this before launch, not after.
5. **"Why does test-editing give REVIEW instead of FAIL?"** Because no checker can tell a repaired assertion from a weakened one, and pretending otherwise would be trusted and wrong; `immutable` *is* a hard violation. Docs: rules.md B7, among the best-written parts. Satisfactory.
6. **"Why does the second task in every repo fail `verify` out of the box?"** Deliberate anti-laundering; `--ack-disarms` with the digest printed at close is the remedy. The answer is defensible but currently lives only in the threat model; README's primary workflow is presented as repeatable and — without the ack — is not. Needs user-facing documentation of the sequential-task loop. Likeliest first-week bug report.
7. **"Who verifies the verifier?"** ~9.5k lines of tests: adversarial lint battery, hook protocol tests with broken-import and casefold probes, golden snapshots, e2e, fail-closed exit discipline. Satisfactory — but the README never mentions the test suite; surface it.
8. **"Why trust a 90-run benchmark?"** Pre-registered, raw JSONL committed, scored from outside, GAMED/ERR classified, and the first campaign's lost rows explicitly downgraded to "testimony" with claims withdrawn — rare candor. Weaknesses a reviewer will still land: n=5 per cell, one fixture family, author-written tasks, and the zero-tamper headline cannot support "agents don't cheat" (deterrence confound, easy tasks). Satisfactory if never overclaimed.
9. **"What if the agent commits its own work or rewrites history?"** The pinned SHA lives outside the brief; `git diff <pin>` sees committed, staged, unstaged, and untracked work alike; re-stamping `base_rev` voids the verdict. Docs complete (B16, ci.md). Satisfactory — volunteer the caveat that arming *after* work is committed vouches for the brief, not the start point.
10. **"Isn't the brief more work than the task?"** Often yes, and SKILL.md concedes it plainly ("anything you'd finish faster than the brief"). The answer is the delegation threshold plus `draft --agent` for authoring. Satisfactory as scoping honesty; weak as growth story — which is why the orchestrator path matters (§3).

## 11. Trust-breaking expectation gaps

Ranked by severity, after adversarial re-verification:

1. **Gitignored-path blindness — SERIOUS PRODUCT GAP + credibility risk.** Live-reproduced twice independently. Undocumented, *and* contradicted by two doc sentences. The fix is a threat-model row, corrected wording, and ideally a ~20-line advisory REVIEW when acceptance commands resolve to repo-local ignored executables.
2. **`verify` dead-ends on `named`/`authoring` briefs — SERIOUS PRODUCT GAP (accidental).** Live-reproduced: a *perfect* agent run under `authoring` exits 1 with acceptance NOT RUN, and no acknowledgement path exists (`--ack-disarms` silences only the repin finding). The REVIEW flag is essential; refusing to even run acceptance is not. This is the modal delegated task dead-ending the flagship verb.
3. **Bash forges a full-strength `pin` — DOCUMENTATION RISK.** Live-reproduced, and the threat model is candid ("every record here is a file"), but the README's headline "needs no cooperation from the agent" doesn't carry the caveat with equal weight. Honest claim: tamper-*evident* against watched tools; tamper-*detectable* only via transcript against shell.
4. **Repin treadmill — DOCUMENTATION RISK, downgraded from an earlier draft.** Deliberate design, working remedy, insufficiently visible outside the threat model.
5. **Acceptance harness files inside `scope` are self-judging — DOCUMENTATION RISK / cheap lint gap.** `scope: [src/cli.py, check.py]` + `acceptance: python3 check.py` lets the agent rewrite its own judge; no rule warns. (The inverse — harness outside scope — is handled correctly and was verified.)
6. **Vendored verifier in-repo — DOCUMENTATION RISK** (§10 Q2).
7. **Untracked artifacts from the verification run itself, `requires:` criteria permanently red locally, no between-tasks reset procedure — minor, ACCEPTABLE with a paragraph each.**

Everything else checked — symlinks, casefold (probed against the live filesystem, stronger than most tools), NUL bytes, two-briefs cross-attribution, CI caveats, fail-open/fail-closed asymmetries per host — is documented accurately. The risk profile is inverted from the usual product: the fine print is honest; the gaps are the places the fine print never looked.

## 12. Product scope verdict

**`CURRENT SCOPE`.** No missing primitive: the checker, the pin, the baseline, the lint, and the benchmark are the right surface, and adversarial review's strongest finding was that the true gap is one days-scale defect plus documentation. Within current scope, the *emphasis* should narrow: the four hook adapters are the most commoditized thousand lines in the codebase (platforms are absorbing prevention) and deserve zero further investment; the checker, the demo, and the benchmark carry the product.

## 13. Three highest-risk assumptions

**Assumption 1: the survives-review failure occurs often enough to trigger adoption.**
Why false: frontier agents under a clear brief showed zero tamper events in 90/90 runs; the event may be too rare, or too invisible, to create demand.
Experiment: passive field study — dogfood plus 5-10 volunteer heavy delegators run `verify` on every real task for four weeks; count catches (violations or REVIEWs a human confirms were real problems).
Evidence required: confirmed catches per 100 tasks, split drift vs. tamper.
Success: ≥1 confirmed real catch per ~25 tasks for at least half the cohort (drift counts — it's the reproducible failure).
Kill: zero confirmed catches across ≥200 real tasks → the verification layer is insurance nobody observably needs; reposition as a contract/brief compiler or fold into a skill.

**Assumption 2: users tolerate the brief loop repeatedly.**
Why false: 2-4 minutes and a digest copy per task, and the live walk found exactly where a daily user quits.
Experiment: same cohort, instrument nothing — ask for their `.prompire/` directory listings and shell history at weeks 1 and 3; count tasks that completed the full loop vs. started it.
Evidence: full-loop completion rate over time.
Success: ≥50% of started briefs reach `verify` in week 3.
Kill: <20%, or users systematically running `prepare` but eyeballing diffs instead of `verify` — that abandons exactly the half carrying the guarantee.

**Assumption 3: the demo converts skeptics to installers.**
Why false: the value may demo well and still read as "I'll write acceptance commands in my prompt, thanks."
Experiment: show the three-beat demo (§9) to 8 target developers cold; then ask them to state what Prompire does that their current setup doesn't, and whether they'd install.
Evidence: unaided articulation of the pinned-contract property; install actions within a week.
Success: ≥5 of 8 articulate the unique property without help; ≥3 install.
Kill: majority describe it as "a prompt template tool" or "like a sandbox" — the category is incommunicable in demo form and positioning must be rebuilt before promotion.

## 14. Launch gate

1. `prompire verify` on a `tests_policy: named` and an `authoring` brief runs acceptance and reports it alongside the REVIEW (exit still nonzero); covered by a test in the suite.
2. `references/threat-model.md` gains an ignored-paths limitation row, and the "git sees the write whatever tool made it" sentences are corrected; `verify` emits at least an advisory when an acceptance command resolves to a repo-local gitignored executable.
3. The `check_scope.py --activate` output no longer claims pre-write refusal unconditionally.
4. A person with no repository knowledge, on a clean machine, goes from the documented install command through the demo and one real brief to a `verify` verdict in under 15 minutes using only the README.
5. The README leads with the reproducibly measured claim (scope drift + explicit contract; benchmark linked), carries the shell-bypass caveat next to "needs no cooperation," and documents the second-task `--ack-disarms` workflow in the primary-workflow section.
6. An executable "why not a shell script" comparison exists showing the naive replication missing an untracked add and a rename-out.
7. `references/hosts.md` states that the verifying copy must run from outside the governed workspace.

## 15. What NOT to build before launch

No fifth host adapter and no further work on the four existing hooks. No CI-mode expansion (it's the honestly-weakest mode; ci.md already says so). Nothing from the neural/ML assessment — the repo's own research doc already concluded no neural method belongs anywhere near the verdict path. No B2B provenance layer (the internal verdict doc's "biggest B2B hole" is real but is a post-traction problem). No web UI, TUI, or dashboard. No new lint rules beyond the self-judging-harness warning. No additional benchmark campaigns beyond keeping the control replicating — the benchmark is already better than the product's distribution deserves. No telemetry of any kind: the post-launch learning loop is GitHub issues with a structured bug template that asks for the `verify` output block and base-source label, a pinned "what did Prompire catch for you / miss for you" discussion thread, and grepping public GitHub periodically for `.prompire/` directories and `prompire prepare` in workflows — that is the whole feedback system an offline CLI needs.

## 16. Final go/no-go recommendation

**Go — continue investing, with the gate above as the boundary.** If this were my project: the core is genuinely well-engineered, the documentation honesty is itself a moat (nobody else in the pre-traction category has a threat model, a pre-registered benchmark, or withdrawn claims), the remaining defects are days of work, and the three questions that actually decide the product's fate — incidence, tolerance, conversion — are unanswerable without launching. Spending further months polishing *before* launch would be optimizing a hypothesis; the launch is the experiment.

What would change my mind: the kill criteria of §13. Concretely — zero confirmed catches across 200+ real field tasks would tell me the verification layer is insurance against a risk too rare and too invisible to sell, and I would fold the brief-compiler half into a skill and stop maintaining the rest; a full-loop retention collapse below 20% would tell me the guarantee costs more attention than delegation saves, which no repositioning fixes; and a demo audience that consistently files Prompire under "prompt tool" would tell me the category cannot be communicated at open-source marketing budgets, however real the property is.
